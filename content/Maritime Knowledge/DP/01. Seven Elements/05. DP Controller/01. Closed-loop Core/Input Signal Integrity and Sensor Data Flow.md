# Input Signal Integrity and Sensor Data Flow

## 한 줄 정의

Input Signal Integrity는 DP로 들어오는 센서값이 믿을 만한지 확인하는 개념이다.

쉽게 말하면 “이 값이 진짜 선박 상태를 말하는 값인가?”를 보는 것이다.

## 제일 중요한 생각

센서값은 현실 그 자체가 아니다.

센서값은 현실을 측정한 결과다.

그래서 센서값에는 항상 오차가 들어갈 수 있다.

```text
실제 바람 / 실제 위치 / 실제 heading
        ↓
센서가 측정
        ↓
전기 신호 또는 데이터로 변환
        ↓
DP 컴퓨터로 전달
        ↓
검사와 필터링
        ↓
DP가 받아들이는 값
```

DPO가 봐야 하는 것은 화면에 보이는 숫자 하나가 아니라, 그 숫자가 어떤 과정을 거쳐 들어왔는지다.

## 센서값은 어떻게 들어오는가

| 단계 | 쉬운 설명 |
|---|---|
| 실제 물리량 | 바람, 위치, heading, motion 같은 실제 상태 |
| 센서 | 실제 물리량을 측정하는 장비 |
| 신호 변환 | 측정값을 전기 신호나 디지털 데이터로 바꿈 |
| 통신 | 케이블이나 네트워크를 통해 DP로 보냄 |
| 입력 인터페이스 | DP 시스템이 그 값을 읽음 |
| 검증 | 값이 말이 되는지 확인함 |
| 필터링 | 짧은 잡음이나 튐을 줄임 |
| 상태 추정 | DP가 사용할 현재 선박 상태를 만듦 |

## 대표적인 전달 방식

중요한 것은 “센서값이 그냥 마법처럼 DP에 들어오는 게 아니라, 신호와 통신을 거쳐 들어온다”는 점이다.

| 방식 | 어디에 쓰일 수 있나 | 조심할 점 |
|---|---|---|
| 아날로그 신호 | 단순한 센서값, 피드백 | 전압/전류 변환 오차, 스케일 설정 오류 |
| 직렬 통신 | 자이로, GNSS, 풍향풍속계 | 문장 형식 오류, 통신 끊김, 지연 |
| 네트워크 통신 | 현대식 PRS, DP 네트워크 | 지연, 패킷 손실, 설정 오류 |
| 장비 간 통신 | 추진기, 전력관리, 기계 장비 | 장비 상태값 해석 오류 |
| 접점 신호 | 준비됨, 운전 중, 고장 알람 | 단순하지만 원인 설명은 부족함 |

## 흔한 오차 종류

| 오차 | 쉬운 뜻 | DP에서 문제 |
|---|---|---|
| 잡음 | 값이 조금씩 흔들림 | 추진기가 쓸데없이 계속 움직일 수 있음 |
| 오프셋 | 항상 조금 틀림 | 위치나 heading을 계속 틀리게 볼 수 있음 |
| 드리프트 | 시간이 지나며 천천히 틀어짐 | 처음엔 괜찮다가 점점 이상해짐 |
| 지연 | 값이 늦게 들어옴 | DP가 과거 상태를 보고 명령함 |
| 끊김 | 값이 안 들어옴 | 기준 위치나 센서 중복성이 약해짐 |
| 튐 | 갑자기 말도 안 되게 변함 | DP가 선박이 움직였다고 착각할 수 있음 |
| 스케일 오류 | 변환 비율이 틀림 | 맞는 신호인데 숫자가 틀림 |
| 부호 오류 | 방향이 반대로 들어감 | 보정 방향이 반대로 갈 수 있음 |
| 좌표 오류 | 축이나 기준점이 틀림 | 힘의 방향, 위치 보정이 틀어짐 |

## 예시 1: 무풍인데 바람이 있다고 나오는 경우

갑판에서 느끼기에는 거의 무풍인데 풍향풍속계가 작은 바람을 계속 보여줄 수 있다.

이 값이 DP의 바람 보정에 들어가면 DP는 필요 없는 추력을 만들 수 있다.

이때 바로 센서 고장이라고 단정하지 말고 다음을 본다.

- 다른 풍향풍속계도 같은 값을 보이는가
- 선박 주변 구조물 때문에 바람이 왜곡되는가
- 값이 계속 일정한가, 순간적으로 튀는가
- 그 값이 들어온 뒤 추진기 명령이 변했는가

## 예시 2: PRS 값이 갑자기 튀는 경우

GNSS나 다른 위치 기준 장비는 순간적으로 위치가 튈 수 있다.

진짜 선박이 움직인 것인지, 위치 기준값만 튄 것인지 구분해야 한다.

확인 포인트는 다음과 같다.

- 다른 PRS도 같이 움직였는가
- 자이로 heading이나 MRU motion과 말이 맞는가
- DP가 그 PRS를 받아들였는가, 제외했는가
- 위치가 튄 순간 추진기 명령도 튀었는가

## 예시 3: 자이로 heading이 틀린 경우

DP는 선박 기준 방향과 지구 기준 방향을 계속 바꿔가며 계산한다.

이때 heading이 틀리면 “어느 방향으로 힘을 줘야 하는지”가 틀어질 수 있다.

특히 PRS 위치는 맞아 보이는데, DP 반응 방향이 이상하면 heading 입력을 의심해볼 수 있다.

## 예시 4: MRU 보정이 틀린 경우

MRU는 선박의 롤, 피치, 상하운동을 측정한다.

이 정보는 안테나나 센서가 흔들리면서 생기는 위치 변화를 보정하는 데 도움을 준다.

하지만 MRU 설치 방향, 기준점, 시간 동기화가 틀리면 오히려 잘못된 보정이 들어갈 수 있다.

그래서 MRU는 “흔들림을 잡아주는 장비”이면서 동시에 “설정이 틀리면 이상한 값을 만들 수 있는 장비”다.

## DP 시스템이 보통 확인하는 것

DP는 센서값을 무조건 믿지 않는다.

- 값이 물리적으로 가능한 범위 안에 있는가
- 너무 빠르게 변하지 않았는가
- 다른 센서와 비교했을 때 말이 되는가
- 센서가 품질 상태를 좋다고 보고하는가
- 짧은 잡음은 필터링해야 하는가
- 이 센서를 얼마나 믿을 것인가
- 아예 제외해야 하는 값인가

## DPO식으로 보는 순서

```text
1. 실제 선박 움직임은 어떤가
2. raw sensor value는 어떤가
3. DP가 받아들인 값은 어떤가
4. 다른 독립 센서와 일치하는가
5. Kalman Filter나 상태 추정값이 튀었는가
6. controller demand가 변했는가
7. thruster command와 실제 feedback이 따라왔는가
```

이 순서로 보면 “센서 문제인지, DP 계산 문제인지, 추진기 반응 문제인지”를 조금씩 좁힐 수 있다.

## 기억할 문장

센서값은 현실이 아니라 현실에 대한 보고서다.

DP 문제를 볼 때는 “값이 얼마인가?”보다 “그 값을 믿어도 되는가?”가 먼저다.
